# Provider waiting proposal — not implemented

This is a design only. Adding a persisted `waiting_provider` state changes claim, recovery and reporting behavior. That conflicts with the instruction not to change existing structural decisions, so no state-machine changes were made. Approval of this design is required before implementation, even locally.

1. A logical provider request has a stable operation identity, existing reservation and hash-bound input. Recheck eligibility, cancellation, budget reservation and fingerprint before every attempt. Do not create a second billable reservation for a retry.
2. Permit **at most two total quick attempts** (initial attempt plus one retry) when every transport attempt is provably pre-send. Use full jitter of 250–1,000 ms before the second attempt, bounded by remaining lease time. The error code alone is insufficient: DNS before connection, all connection attempts before TLS, or a fully instrumented failed TLS handshake with zero application bytes and no earlier pooled/retried/redirected dispatch are required.
3. After two provably pre-send failures, atomically save the provider-wait reason and next retry time, mark `waiting_provider`, and release the lease. Suggested delays are 5, 10, 20, then 30 minutes, plus 0–60 seconds jitter. This permits recovery after a 10-minute outage without exhausting task attempts in seconds. Keep a separately bounded overall wait horizon (proposed 24 hours), then request review rather than silently failing or retrying forever.
4. At the next eligible time, reacquire a normal new lease through existing exclusive-claim mechanics, bound to the same logical operation/reservation and unchanged fingerprint. The old lease must never be reused after release. Preserve approval/hash gates. Existing JSON can hold `provider_wait` metadata such as reason, attempt count, first failure and next retry; no new table or webhook is needed.
5. Do not count provider-wait cycles as lead-quality failures. Reports should show “Waiting for provider”, provider-wait reason and next retry time, not “Failed”. A cancellation or changed fingerprint supersedes the waiting operation and follows existing reservation reconciliation rules.
6. Ambiguous dispatch, post-send reset, response timeout or unknown previous send history must not enter automatic resend. Reconcile a provider run/idempotency reference if supported; otherwise stop in needs-review. A reservation expiring or being released while waiting also requires reconciliation; it must not silently create a new reservation.

The control probe is insufficient to prove whole-logical-request pre-send status. Fetch may reuse sockets and both clients may wrap errors. Complete phase instrumentation and provider idempotency/reconciliation support are **UNVERIFIED**. No retry or waiting-state implementation is included in this change.
