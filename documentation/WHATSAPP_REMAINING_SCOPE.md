## Verified constraints

- The React Login page permits local demo login on backend failure. That state is not authenticated organization membership and cannot authorize Meta account/credential management.
- Existing activity dispatch metadata requires a plan/step. An unsolicited incoming conversation has neither. Generating a dummy plan or attaching it to an arbitrary campaign would misrepresent its origin.

## Incoming storage extension — local and scratch only

The user authorized implementation and scratch testing of the narrow exception. Migration `047_whatsapp_inbound.sql` implements a distinct incoming record type in existing `outreach_activities`; it is **not applied live**. Actual scratch schema permits a null lead. Incoming records carry org, sender connection, WABA, phone-number ID, provider message ID, timestamp, bounded text and an unsupported-content flag. They cannot carry a plan, step, lease, reservation, sending status or sending receipt. The existing dispatch constraint is preserved for other records.

The partial unique index deduplicates organization + sender identity + provider message ID. Organization is derived from a unique current trusted campaign sender binding; callback org values are ignored. Unknown/shared/ambiguous bindings are rejected. Matching replays are idempotent; changed replays fail. A failed event rolls back its whole batch. Standalone STOP blocks later WhatsApp dispatch to that phone in the organization; later ordinary replies cannot clear it. Other incoming contacts require review before further automatic outreach. A bounded, org-scoped SQL inbox reader is included, with no public endpoint. Migration 050 now adds private membership-authenticated inbox reads, admin acknowledgement/archive and body redaction, optimistic revisions and bounded audit history. These actions preserve the existing review hold and STOP. Optional retention defaults to a dry run and redacts bodies in bounded batches without deleting opt-out or deduplication identity. Real customer login/membership configuration and public integration remain unfinished. The installed callback still uses 046 behavior until 047 is separately approved and applied.

Scratch validation: `node scripts/diagnostics/whatsapp-scratch.cjs --inbound`, isolated network-none container `lead_diag_pg_20261011`, database `scratch_email_release_20261019`, transaction rolled back. Tests cover sender routing, org isolation, duplicate/conflicting events, malformed input, atomic batches, incoming-only constraints and persistent phone opt-out. The 68 offline WhatsApp tests also pass. These checks do not verify real Meta delivery or customer authentication.

## Follow-up templates

Local preparation is implemented in `scripts/whatsapp/sequence.cjs` and embedded in the local 06C Code bundle. Optional campaign JSON `whatsapp_dispatch.templates_by_step` maps sequence step numbers to complete approved template snapshots. Step 1 may use the existing `template`; later steps require their own explicit snapshot. Every template passes the existing consent, sender, freshness, variable, URL, claim, quote and limit checks. Exact repeated messages are rejected. All steps, rendered messages, snapshots and delays are included in `artifacts.whatsapp_sequence` before the normal plan hash is computed. No approved stored plan is modified. Mixed-channel sequences are blocked pending cross-channel predecessor checks; they are not silently renumbered.

Migration `048_whatsapp_followups.sql` now implements the requested-step gate, previous-confirmed-send and due-time checks, per-step claim metadata and due-only queue **locally, unapplied**. It retains the 047 phone suppression wrapper and 046 approval, lease, quote, working-window and organization budget checks. Prior acceptance must belong to the same org, lead, plan hash, predecessor artifact, recipient and connection; attempting, uncertain and failed predecessors cannot unlock another step. Claims retain the selected step and template; duplicate claims remain blocked. Mixed-channel sequences remain blocked. No workflow node/connection change was needed for these SQL contracts. The installed 046 gate still rejects later steps.

**Release blocker: multi-day template freshness versus immutable plan approval.** Current rules require a template check less than 24 hours old and exact equality between current campaign template JSON and the snapshot inside the approved plan. A later refreshed `checked_at` changes that equality (and may invalidate the campaign fingerprint); keeping the old timestamp expires the check. Therefore a three-day follow-up is not deployable through the current refresh process, even if template content is unchanged. Scratch explicitly tests that stale matching snapshots stay blocked. The due-path tests isolate scheduling by supplying fresh fixture evidence; they are not proof that a real multi-day campaign can pass. Do not deploy 048 as complete follow-up support or extend freshness/alter approved plans to hide this conflict.

Local resolution implemented in unapplied migration `049_whatsapp_recheck.sql`: separate immutable template content from a fresh, credential-bound provider observation stored under the predecessor activity's `dispatch_metadata.whatsapp_rechecks[step]`. The approved template/campaign JSON stays untouched, including its original `checked_at`. Only a fresh (under 24 hours), same-content observation for the same org, plan hash, step, predecessor and sender can satisfy current provider freshness. Variable order is compared exactly. Changed/rejected content blocks and requires review. Credential expiry, quotes, releases, consent, budgets, working windows, plan expiry, fingerprints and approvals still pass their original checks; rechecks cannot extend them. No new table/webhook or fingerprint exception is added.

The local worker now has a separate `providerRechecksEnabled` switch (default false). A due stale candidate can obtain its trusted SQL recheck input, make at most two fixed read-only Meta GETs (account phone list, then first template page), persist the observation, re-enter the full gate and only then use the existing atomic claim/transport. Template pages are not followed to arbitrary URLs; missing/paginated/ambiguous matches fail closed. The GET-only HTTP adapter keeps TLS hostname verification, bounds streamed responses to 256 KiB, times out after 10 seconds, redacts errors and does not retry. The sending adapter remains POST-only. A newer failed check supersedes older positive evidence; older evidence cannot overwrite it. Failed checks back off for 30 minutes and a tick performs at most one provider recheck. Rechecks create no message reservation and no model/provider spending ledger entry. The normal message reservation/claim occurs only after re-gating.

It asserts an aged, approved fixture can pass a fresh same-content check **without any change by the store function to plan body/hash, context fingerprint or approvals**. It also covers failure replacement, older-positive rejection, expiry, wrong-org/sender/hash, changed body/variable order, unexpected credential fields, candidate reachability and backoff. Mocked worker tests exercise the read/persist/re-gate/claim path without real network traffic. Real Meta recheck execution and installation of this local custom-node revision remain UNVERIFIED; all live workflows and runtime files remain unchanged.

Scratch command: `node scripts/diagnostics/whatsapp-scratch.cjs --followups`. Applies 046/047/048 only in the existing network-none scratch database, exercises baseline/inbox/follow-up assertions, and rolls back. Tests include unapproved/hash-changed plans, skipped predecessors, uncertainty, delayed eligibility, failed delivery, changed provider status, malformed approved sequence JSON, shared reservation ceilings, reply stops, duplicate claims and actual selected-step persistence. Provider template approvals and real delivery for these drafts are UNVERIFIED. Local builds preserve workflow connections, sticky notes, modes and non-Code settings; no import or activation occurs.

Prepare a template snapshot and exact rendered message for each sequence step before hashing/approval. At dispatch recheck provider approval/current content, consent, suppression/replies, previous-step acceptance, due time, working window, plan hash, reservation and budget. Never repeat the first template automatically as a follow-up. Change only WhatsApp-specific gate/queue logic; preserve existing email/call behavior.
